# Security review

Each row states where the protection actually lives in the codebase, not just that it exists.

| Threat | Where it is handled |
|---|---|
| SQL injection | Not directly applicable (MongoDB, not SQL), but the equivalent NoSQL injection risk is handled the same way: every query goes through Mongoose's query builder with typed, schema-validated inputs. No query is ever built by concatenating a string from user input. |
| XSS | `src/middleware/validate.ts`, `sanitizeInput()`, applied globally to every request body and query string in `src/routes/index.ts` before any controller runs. HTML-significant characters are escaped on the way in. |
| CSRF | This API is stateless bearer-token auth (`Authorization: Bearer <token>`), not cookie-based sessions, so there is no ambient credential for a third-party site to ride along with. CSRF tokens are a mitigation for cookie auth specifically; they do not apply here because the attack they prevent is not possible against this auth model. If a browser-based session-cookie flow is added later, CSRF tokens and a `SameSite` cookie policy would need to be added at that point. |
| Rate abuse | `src/app.ts`, `express-rate-limit` applied to the entire `/api/` prefix, window and max request count configurable through `RATE_LIMIT_WINDOW_MS` and `RATE_LIMIT_MAX`. |
| Credential leaks | `.env` is git-ignored. `src/config/index.ts` fails startup immediately if a required secret is missing, so the system cannot run on a default or empty secret. One real credential leak was found and fixed during this review: a live Redis connection string, including its password, had been committed into `.env.example`. It has been replaced with a placeholder. That credential must still be rotated on the Redis provider's side, since it was already pushed to the repository's history. |
| API key exposure | Any third-party credential that needs to be stored (as opposed to read from environment at request time) is encrypted at rest with AES-256-GCM before being written to the database (`src/lib/encryption.ts`). Backups are encrypted with AES-256-CBC before being written to disk (`src/services/backup.ts`). |
| Duplicate processing | `signals.dedupHash` carries a unique index at the database level (`src/models/Signal.ts`), so a duplicate cannot be inserted even if the application logic that checks for one has a bug. Ingestion itself also checks for an existing record before inserting, inside a transaction. |
| Invalid data | Every connector's `normalize()` output passes through `validate()` before it is allowed to reach the database; anything that fails is logged and skipped, not coerced into something that looks valid. Every API request body is validated against a Zod schema before it reaches a controller. |
| Broken jobs | Failed jobs are retried up to 3 times with exponential backoff, then retained (not deleted) in BullMQ's failed set, which is this system's dead letter mechanism. `GET /connectors/failed-jobs` makes that set reviewable rather than a bare count, so a stuck or broken connector is visible. |
| Authentication | JWT access and refresh tokens (`src/controllers/auth.controller.ts`), verified on every protected request in `src/middleware/auth.ts`, which also re-checks that the user still exists and is active on every request rather than trusting the token's claims alone. |
| Authorization | Role based, implemented as a single data-driven permission map (`ROLE_PERMISSIONS` in `src/middleware/auth.ts`), checked server-side on every write endpoint through `requirePermission()`. A client-supplied role claim is never trusted without this server-side re-check. |
| Audit logs | Every login attempt (success and failure), registration, admin-created user, signal review, connector trigger, connector state change, and backup export or restore writes an entry to the append-only `audit_logs` collection, including the acting user, the ip address, the request id, and the outcome (`src/lib/logger.ts`, `auditLog()`). This was found to be logging to file only, not to the database, during this review, and has been fixed to persist to both. |
| Backups | `POST /backups/export` and `POST /backups/restore`, encrypted at rest, with a tested restore path (`docs/RUNBOOK.md` walks through it). Restore filenames are resolved with `path.basename()` before use, which prevents a path such as `../../etc/passwd` from escaping the backups directory. |
| Encrypted credentials | Covered above under API key exposure. |
| API key rotation | See `docs/RUNBOOK.md` for the rotation procedure. |

## Findings from this review that required a fix

1. A live Redis credential was committed in `.env.example` and pushed to the repository. Removed and replaced with a placeholder. The credential itself must be rotated on the provider's side regardless, since removing it from the file does not undo its exposure in git history.
2. `package.json` pinned `typescript@^7.0.2`, a version that does not exist as a stable release and conflicts with `ts-jest`'s peer dependency. This blocked `npm install` entirely for anyone cloning the repository fresh. Fixed to a pinned stable `5.9.x` release.
3. The BullMQ queue name (`atlas:ingest`) contained a colon, which the installed BullMQ version rejects since colons are reserved as its internal Redis key delimiter. This would have crashed on first startup in any real environment. Renamed to `atlas-ingest`.
4. Audit events were written to log files only, never to the `audit_logs` database collection that exists specifically to hold them, making the audit trail unqueryable in practice. Fixed to persist to both.
5. The public `/auth/signup` endpoint contained a role-escalation code path that checked `req.user?.role === 'ADMIN'`, but the authentication middleware was never applied to that route, so `req.user` was always undefined and the branch could never execute. It looked like a working permission check and was not one. Removed, and replaced with a real, working `POST /users` endpoint that is genuinely gated behind an authenticated admin.

## What was verified directly, not just reviewed by reading

- The full test suite (39 tests across 5 suites) passes, covering the permission matrix, input sanitization, request validation schemas, secret encryption round-tripping and tamper detection, and the connector registry's registration and failure-isolation behavior.
- The cache layer (`src/lib/cache.ts`) was exercised against a live Redis instance: set, get, invalidate, and the cache-aside `withCache()` helper all behaved as documented.
- The ingestion queue (`src/queues/ingest.queue.ts`) was exercised against a live Redis instance after the naming fix: jobs enqueue, the waiting count reflects them, and the failed-jobs read path used by `GET /connectors/failed-jobs` returns correctly.
- The GitHub connector was run against the real GitHub API: health check passed, a real batch of records was fetched, and a sample record passed validation.
- The RSS and HackerNews connectors could not be exercised against their live sources from this environment, because its network access is restricted to a fixed set of domains that does not include theirs. Their code paths mirror the GitHub connector's structure and pass the same validation logic in the automated tests, but a live run against `hn.algolia.com` and the configured RSS feed URLs should be done in a normal development environment before this is considered fully proven end to end.
- MongoDB itself was not available in this environment (not installable from the default package repositories, and MongoDB's own installers are outside the allowed network range), so the full end-to-end ingestion path, the seed script, and the benchmark script could not be executed here. Section "Scale verification still required" in `docs/RUNBOOK.md` gives the exact commands to run these in a real environment with database access.
